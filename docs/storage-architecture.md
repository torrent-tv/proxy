# Proxy storage policies

The proxy has one `MachineBudget` owner for memory and disk. Memory is one resource; disk is divided separately for each physical device, identified from the storage directory. A claimant reports bytes already held and bytes it currently wants. Pending reservations count before a write starts. The owner divides only the allowance for that resource and passes each share to the store that owns those bytes.

## Representations and lifetimes

| Representation | Owner and identity | Reuse, expiry and pressure behavior |
|---|---|---|
| Original input ranges | `OriginalInputStore`, keyed by source and file; identical ranges are shared by readers | Held while admitted encode requests own them; released when requests are withdrawn or their runs end. Admission reports required bytes and pending input demand to the memory budget. |
| Parsed media metadata and keyframe tables | `SourceFiles`, `IndexMemory`, and `KeyframeTables`, keyed by source file | Shared by sessions for the same file. Memory is budgeted; unused records and tables are released during session cleanup. |
| In-memory torrent pieces | `SharedPieceStore`, one store per torrent | Memory blocks and pending piece admissions are counted. Pieces are selected by live priority ranges and recency; pinned reads are protected. Free blocks are reused while within the allowance and released when the ceiling shrinks. |
| Spilled torrent pieces | `PieceDiskStore`, one file per piece within a torrent store | The disk budget is shared with other claimants on that device. Eviction uses reader position, priority and recency; active reads are protected. When a torrent has been idle for `IDLE_KEEP_MS`, the torrent and its piece store are removed. |
| Completed source files | `CompletedFiles`, keyed by torrent hash and file index | One complete file is shared by HTTP reads and encoders. Its byte reservation is made before writing. Concurrent writes cannot spend the same allowance twice. Active read leases prevent removal. Unused files expire after `IDLE_KEEP_MS`; disk pressure can evict the least recently used eligible file earlier. If a full file is retained, duplicate spilled pieces are removed. |
| Generated HLS segments | `SegmentStore`, keyed by output and segment number | Sessions that produce the same output share files. The lifecycle owner expires outputs after `IDLE_KEEP_MS` without demand and can evict segments by viewer position under disk pressure. Active reads and the segment currently used by a viewer are protected. A measured zero allowance remains distinct from a missing measurement. |
| In-progress HLS segment files | Encoder run, named `making-<run>-<index>.mp4` until publication | Not served or adopted as complete. Run cleanup removes its temporary files; startup removes unfinished files left by a killed process. |
| FFmpeg input cache files | FFmpeg cache for one encode run | Counted on the device where FFmpeg writes them and treated as required for the lifetime of the run. Run cleanup removes the cache directory. This cache is temporary and separate from reusable completed source files. |
| Diagnostic artifacts | `Diagnostics`, on the configured diagnostics device | Measured and budgeted separately from media. When its share is full, new captures are refused and logged; existing evidence is not removed to make room. Kernel core dumps are measured but cannot be refused by the proxy. |
| In-progress completed-file writes | `CompletedFiles`, a unique `<index>.partial-<pid>-<id>` file within a torrent directory | The complete target length is reserved before bytes are written. The partial name is never served. A failed write removes it. Startup removes a partial only after its owner process has exited; legacy partials without an owner are removed after the idle period. |

The shared one-hour idle period is a chosen interim limit, not a measured viewer-return threshold. The proxy records returns from existing output files, but a full week of ordinary use has not yet established a replacement value. Completed-file access time is held in process memory; adopting completed files after a proxy restart starts their idle period again. This avoids deleting a file early when its prior access time was not persisted, at the cost of up to another hour of retention after restart.

## Avoiding duplicate work and storage

1. Consumers with the same source-file identity use the same `SourceFiles` entry, parsed tables, and shared original-input ranges. Pending range preparation is keyed and coalesced by `EncodeInputs`.
2. Consumers with the same output key use the same `SegmentStore` inventory and published files. The output key includes the media and encoding choices that determine segment compatibility.
3. A completed source file answers later reads directly. Once its write is confirmed, its duplicate spilled pieces are dropped. A read lease keeps the file present until the response ends or is cancelled.
4. A spill write temporarily holds a memory block and a disk file on different resources. The block is returned after the write; both physical allocations are accounted on their respective resources while they overlap.
5. FFmpeg's input cache is an operation-scoped working copy. It is retained only while its run needs it and removed by run cleanup; it is not a second reusable media cache.

## Evidence and limits

On 2026-10-18, field verification on Home Assistant saved a 737 MiB LostFilm episode as a completed source file in 18.9 seconds. After removing only its generated HLS output, playback regenerated the output from that completed file: the source was complete, there were zero planned or unknown pieces, the measured download rate was zero, and the piece store reported zero spilled bytes. The tab ran for 86 seconds without a playback error. This confirms reuse of the saved file without another torrent download and confirms that the completed file and its duplicate spilled pieces were not retained together.

A separate 2026-10-18 check saved a 1,310 MiB episode in the completed-file store and replayed it with zero spilled pieces and no new torrent. The field checks do not establish the one-hour return period or the maximum aggregate disk demand over a long period.

After publishing proxy 2.101.24 and installing add-on 0.94.24 on Home Assistant, a fresh field run saved `Haunted.Hotel.S02E01.720p` as a 772,333,103-byte completed source file. Selecting the same torrent again started playback from that file: readiness was true with zero delay, 10.375 s buffered, zero planned or unknown pieces, and a measured download rate of 0 B/s. The browser advanced through 38.6 s without a media error; the WebTorrent piece directory was empty while the completed file and generated HLS output existed. The check then replayed `Haunted.Hotel.S02E02.1080p`, sought to 774 s, and observed playback continue at 777.8 s without an error. During that download and HLS generation, disk use was 754,248 KiB for completed files, 462,560 KiB for torrent pieces, and 970,564 KiB for generated segments; there were no completed-file partial writes at the sampled time. The second episode had not finished downloading, so the field snapshot measures active piece and segment writes, not the brief whole-file assembly write. Closing both tabs and deleting only their temporary files left no media in those three test directories. The first episode's initial low-rate estimate briefly exceeded 100,000 hours before measurements recovered; estimate accuracy remains tracked by #ttv-185. The field checks do not wait out the one-hour expiry period; no-torrent tests cover that timer and the active-read protection.

The storage classes keep distinct eviction rules because losing them has different costs: a spilled piece may be downloaded again; a completed file may be reconstructed from its torrent; a generated segment may require encoding again; a diagnostic artifact may be the only record of a failure. The common policy is the machine-level budget and device accounting, not one eviction order for every data type.
